# V0.4.0 Design — Benchmark Suites and Reproducible Evaluation

This document describes the design of the benchmark suite system added in
V0.4.0. It builds on the V0.3.1 engine without replacing any of its parts.

## Goals

- Organize, run, version and compare multi-task benchmark protocols.
- Make a run exactly reproducible at the protocol level through an immutable
  lockfile (`benchmark.lock.json`).
- Manage datasets (local import, controlled remote import, deterministic
  sampling) with provenance and license care.
- Keep every V0.3.1 guarantee: evaluator budgets, latency separation,
  per-evaluator statistics, reevaluation provenance, comparability warnings,
  Docker isolation, secret masking.

## Non-goals

- No second benchmark engine: suite runs orchestrate `run_benchmark()`.
- No plugin system, database, server, authentication, leaderboard or telemetry.
- No mandatory Hugging Face dependency; remote import uses the standard
  library HTTP client and explicit user action.

## Suite data model

A suite is a directory containing a `suite.yaml` definition and its datasets:

```text
mini-general/
├── suite.yaml
└── datasets/
    ├── arithmetic.jsonl
    └── ...
```

`SuiteDefinition` (Pydantic, `extra="forbid"`):

- `id` (kebab-case identifier), `version` (semver), `name`, `description`.
- `license` (SPDX identifier or custom text) and optional `source`,
  `author` provenance fields; both are required to *publish* a suite but
  built-in demo suites document their scope honestly.
- `defaults`: protocol parameters (`repeats`, `seed`, `concurrency`,
  `timeout`, `max_tokens`, `temperature`, `shuffle`) — the same fields as the
  engine `Defaults`, minus provider credentials.
- `tasks`: list of `SuiteTask` — `id`, `dataset` (relative path),
  `weight` (default 1.0, positive), optional `description`, optional
  `expected_metric` (validation: every entry of the dataset must use it).
- `evaluators`: optional judge/code block reusing the engine
  `EvaluatorsConfig`, so a suite can require the judge rubric or the Docker
  code runtime.

Constraints enforced at load time:

- unique suite `id` per registry, unique task `id` per suite;
- semver `version`; unique positive weights are not required to sum to 1
  (weights are normalized, and reported alongside raw values);
- `dataset` must be a relative path inside the suite directory (no absolute
  paths, no `..` escape, no symlink escape);
- rubric paths referenced by a suite are resolved and fingerprinted at load
  time.

## Registry

`minieval_bench.suites.registry` discovers suites in two places:

1. built-in suites shipped inside the wheel under
   `minieval_bench/builtin_suites/<id>/` (read through
   `importlib.resources`);
2. user directories listed in the `MINIEVAL_SUITE_PATH` environment variable
   (`os.pathsep`-separated) and in the optional `--path` option of
   `suite list`.

`suite list` / `suite info` / `suite validate` never execute anything found in
a suite: discovery only reads `suite.yaml` and, for `info`/`validate`, the
dataset files. Validation reuses the engine's dataset validation
(`DatasetEntry` validators: regex compilation, JSON Schema check, test module
compilation and test-name extraction) so a validated suite is runnable.

## Parameter inheritance

Priority order (highest first):

1. Suite protocol: datasets, weights, expected metrics, evaluators (rubric,
   code config). Never silently overridable.
2. Suite `defaults` (repeats, seed, concurrency, timeout, max_tokens,
   temperature, shuffle).
3. User CLI overrides on `suite run` (`--repeats`, `--seed`,
   `--concurrency`, `--timeout`, `--max-tokens`, `--temperature`,
   `--shuffle/--no-shuffle`, `--sample`, `--sample-seed`,
   `--sample-mode`).
4. Engine defaults.

Any user override is recorded in the suite manifest and in the lockfile
(`user_overrides` block), and the run is flagged `protocol_modified: true`:
a modified run is never presented as the official suite version.

## Dataset handling

- Suite datasets are JSONL files validated by the existing `DatasetEntry`
  model. `DatasetEntry` gains one additive optional field: `category`
  (string) used by stratified sampling.
- `dataset validate` checks a standalone JSONL file.
- `dataset import` converts local CSV or JSON to JSONL with deterministic,
  documented transformations; CSV supports the deterministic metrics and
  `judge` (reference-optional). JSON Schema and code-test entries must be
  authored as JSONL directly.
- `dataset import-hf` downloads one file of a Hugging Face dataset at an
  immutable revision (a full commit sha is required; branch names are
  rejected with an explanation), with a size limit, no archive extraction
  and no code execution. Provenance (source, revision, sha256, license and
  how it was determined, date, transformations) is written next to the
  imported file as `<name>.provenance.json`.
- The import cache lives under `~/.cache/minieval-bench/` (override:
  `MINIEVAL_CACHE_DIR`).

### Sampling

`--sample N` selects a deterministic subset: entries are sorted by id, then
drawn with `random.Random` seeded from
`sha256("<sample-seed>:<dataset-sha256>")` — independent from the global
Python RNG, identical for every model, stable for an unchanged dataset.
`--sample-mode stratified` requires every entry to carry a `category` and
allocates the sample proportionally per category. The method, seed, count,
selected ids and source fingerprint are recorded in the lockfile, and reports
label the run as a subset, never as the full suite score.

## Suite runner

`suite run <id> --config models.yaml --output results/<id>/`:

1. resolve and validate the suite, load datasets, verify fingerprints;
2. build the execution plan: one engine run per task, models taken from the
   models file (`ModelsFile`: a plain `{models: [...]}` reusing
   `ModelConfig`);
3. count planned candidate calls and judge calls, apply `--max-calls`
   refusal and the V0.3.1 judge budget pre-checks (per task, since budgets
   are per engine run);
4. `--dry-run` prints the plan, evaluator requirements (Docker, judge),
   missing dependencies, cost estimates when pricing is configured
   (documented word-count heuristic; `n/a` otherwise) and methodological
   warnings — fully offline, no provider call, no Docker start;
5. execute tasks sequentially with `run_benchmark()`, writing each task
   under `tasks/<task-id>/` (existing report format: `results.json`,
   `manifest.json`, `report.md`, `report.html`);
6. write suite-level artefacts (`suite-manifest.json`,
   `benchmark.lock.json`, `suite-results.json`, `suite-report.md`,
   `suite-report.html`).

Trial identity stays unique even when two tasks reuse entry ids: each task
is a separate engine run stored in its own directory, and suite-level
aggregations key on `(task, model, question)`.

Task status: `completed` (all planned trials succeeded and evaluated),
`partially_completed` (ran, but some trials or evaluations failed),
`unavailable` (dataset, evaluator or dependency missing — never scored as
zero), `infrastructure_failed` (unexpected engine error), `not_executed`
(remaining tasks after an interruption). A suite with any non-completed task
is never reported as fully validated.

### Interruption and resume

Task reports are written atomically (temporary directory renamed into
place). After an interruption, `suite run --resume` reuses a task result
only if the recomputed lockfile section for that task matches the stored
one (dataset fingerprint, evaluators, models, parameters, sampling);
otherwise the task is re-executed. The suite manifest records which tasks
were reused. Plain `suite run` without `--resume` re-executes everything.

## Aggregated statistics

Per task and model, the runner reuses `ModelStats` unchanged. Suite-level
aggregation groups tasks by *metric family*:

- `deterministic` (`exact_match`, `contains`, `regex`) — binary;
- `json_schema` — binary;
- `code_tests` — binary plus test counts;
- `judge` — score mean.

Within a family, two averages are computed when coverage allows:

- macro: weighted mean of per-task rates (weights documented and
  normalized);
- micro: pooled successes over pooled evaluated trials.

Heterogeneous families are never merged into a global score. Tasks with
status `unavailable` or `not_executed` contribute no observations and are
shown as missing coverage rather than zeros. Every aggregate carries the
number of tasks and trials it covers.

## Reproducibility lock

`benchmark.lock.json` is a deterministic JSON document (canonical
serialization, sorted keys, no timestamps, no absolute paths) covering:

- MiniEval version; suite id, version and definition fingerprint
  (sha256 of the canonical suite definition);
- per task: id, weight, dataset reference and sha256, selected ids after
  sampling, sampling block, per-entry fingerprints of JSON schemas and code
  tests, expected metric;
- generation parameters (effective defaults after overrides), user override
  list, model configurations;
- evaluator blocks: judge (rubric fingerprint, version, criteria, model,
  repeats, budgets) and code (full config including the image digest);
- statistics configuration.

Identical protocol inputs produce byte-identical lockfiles. `suite verify`
recomputes the lock from the current suite, datasets and models file and
reports every difference (dataset modified, sampling changed, configuration
changed, missing file, suite version drift). It never calls a provider.

Reproducibility is protocol reproducibility: identical data, parameters and
evaluators. It does not promise identical outputs from a hosted model, which
can change server-side; reports and docs state this limit.

## Suite comparison

`suite compare --run A --run B` loads both lockfiles and results:

- identical protocol (equal lockfiles) → per-task model comparison with
  score/latency/cost differences and paired per-question statistics
  (reusing the V0.3.1 paired machinery, per task);
- different protocol → precise list of differences, no deltas, no ranking,
  individual results still browsable.

## Export and sharing

`suite export --input results/<id>/ --output archive.zip` produces a zip
with the suite manifest, lockfile, aggregated results, per-task stats and
reports, plus a `checksums.json` (sha256 per member) allowing integrity
verification against a reference. Default mode excludes individual
responses; `--include-responses` adds per-task trials after an explicit
secret scan (existing masking patterns refuse the export on match).
Hashes verify integrity, not producer identity; no cryptographic signature
is implemented in this version.

## Compatibility

- All V0.3.1 commands and artefacts are unchanged; old runs remain readable
  (`Manifest` gains only optional suite-related fields).
- `DatasetEntry.category` is optional and additive.
- The wheel packages `builtin_suites/` and the new templates the same way
  the existing `templates/` directory is packaged.

## Risks and residual limits

- The Docker code-eval residual risk documented in V0.3.1 is unchanged;
  the experimental `mini-code` suite keeps the explicit activation flag,
  the pinned digest and all runtime restrictions.
- Remote dataset imports depend on the remote host staying available and
  honoring immutable revisions; the lockfile records the exact revision.
- Cost estimates in dry runs are heuristics based on configured pricing,
  never measurements.
