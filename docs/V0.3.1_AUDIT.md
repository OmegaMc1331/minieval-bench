# V0.3.1 audit — reliability, security and evaluation integrity

This document records the defects confirmed in v0.3.0, their root cause,
the corrections applied in v0.3.1 and the validation evidence. Every
defect listed below was reproduced or demonstrated on the code as tagged
`v0.3.0` before being fixed; regression tests were added alongside each
correction.

## Method

The audit covered `runner.py`, `models.py`, `providers.py`, `reports.py`,
`comparison.py`, `cli.py`, `html_report.py`, the whole `evaluation/`
package, the test suite, the CI workflows, the examples and the v0.3.0
design notes. Each defect was confirmed by reading the exact execution
path, then by a test that fails against v0.3.0 and passes after the fix
(where a unit-level reproduction is possible), or by a Docker integration
test for container-only behavior. Defects described in the mission
briefing that turned out to be already handled are listed at the end with
the evidence that no change was needed.

## P0 — Code evaluation verdict integrity

### Confirmed defect

`parse_harness_output()` in `evaluation/code.py` scanned the container's
stdout and accepted the first line starting with `{`. The evaluated
program ran in the same Python process as the harness and shared its
stdout: a submission could print a forged verdict object before the
harness printed the real one, and the host accepted the forgery. A
submission could also define extra `test_*` functions that counted as
passing tests.

Reproduction (v0.3.0): a submission printing
`{"status": "completed", "tests": []}` was accepted verbatim, and a
submission defining a trivially passing `test_injected()` inflated the
reported test set.

### Correction

The in-container harness was split into two processes:

- a **worker** process (`python -I -c`, payload on stdin) that executes
  the submission and the tests in one namespace and reports per-test
  outcomes on a **dedicated pipe fd** passed by the controller; its
  stdout and stderr carry only program noise;
- a **controller** process (`python -I -`, script on stdin) that spawns
  the worker, enforces time and byte caps, collects the worker report on
  the report pipe, and prints the **single verdict line** the host
  parses. Nothing else can write to that channel: the worker runs with
  its own std pipes and does not inherit the controller's stdout.

The host then validates the verdict structurally: statuses are checked
against a fixed vocabulary, per-test names must exactly match the
dataset's test functions (derived by AST from the tests module), and
duplicates, unknown names or an empty reported set are rejected as a
harness integrity failure (evaluator status `failed`, never a model
success). A run with zero executed tests cannot produce a perfect score.

### Threat model and guarantees

Guaranteed by process boundaries and validation:

- The channel the host parses is written only by the trusted controller
  process; the evaluated program does not hold that file descriptor.
- Accidental or deliberate prints, including forged JSON verdicts, never
  enter the report pipe; they are capped and discarded as noise.
- Test identity and count are enforced against the dataset tests, so the
  submission cannot add, rename or drop tests without failing the run.
- A worker killed by the program, by the wall-clock timeout, by the
  memory limit or by an output overflow produces distinct outcomes
  (`worker_crashed`, `timeout`, `worker_killed`, `output_overflow`), all
  scored as non-passing, never as success.

Residual risks (documented, accepted):

- The submission runs inside the worker process. A determined adversary
  can inspect worker memory (for example through `gc` iteration) or
  `/proc` to discover the report pipe and the test names, and forge a
  structurally valid report. Raising the bar (`-I`, payload via stdin
  rather than argv, report on a non-standard fd, tracing hooks cleared)
  does not eliminate this: exec-based isolation inside one OS process
  cannot be made airtight. The verdict *channel* and the verdict
  *decision* remain trusted; the per-test outcomes rely on the worker's
  integrity.
- Per-test timeouts use `SIGALRM` and therefore work on Linux containers
  only; on other kernels a hanging test is bounded by the wall-clock
  timeout.

### Validation

`tests/test_code_docker.py` (executed for real under Docker, see the
validation section) covers the twelve adversarial scenarios: correct
program, incorrect program, syntax error, runtime exception, plain
stdout text, forged verdict, multiple forged verdicts, injected test
functions, report-pipe fd spray, worker kill, malformed output and
`SystemExit`. Manipulation attempts never produce an artificial success.

## P0 — Bounded Docker output capture

### Confirmed defect

`DockerCodeRunner.run()` used `subprocess.run(capture_output=True)` and
truncated the buffers **after** capture. A program emitting gigabytes
would be fully buffered in host memory before truncation; only the
container memory limit (which kills the run) stood in the way.

### Correction

Both the host side and the in-container controller now read through
bounded readers: at most `max_output_bytes` are retained per channel,
overflow is detected explicitly (`output_overflow` outcome, distinct from
`timeout` and `memory_limit`), and the producing process is killed when
the cap is exceeded. Reader threads drain stdout and stderr concurrently
so pipes cannot deadlock, and the container is force-removed (`docker
rm -f`) in a `finally` block covering every exit path: normal
completion, wall-clock timeout, output overflow, docker failure and
controller exceptions.

### Validation

Docker tests cover small output, output exactly at the limit, output
over the limit, an unbounded continuous stream and a large stderr
stream; an autouse fixture asserts after every test that no
`minieval-eval-*` container remains. A measured run on the development
machine (Windows host, Docker Desktop 29.6.1) with a container producing
512 MB against a 64 KB cap kept the host process working set at
36.2 MB against a 35.5 MB baseline over 1206 samples — the capture is
bounded in practice, not only by inspection.

## P0 — Latency measurement

### Confirmed defect

`run_trial()` measured `latency_ms` from just before the provider call
to after `evaluate_response()`. With a remote judge or the Docker
sandbox, evaluation time inflated the reported model latency.

Reproduction: the regression test
`test_run_trial_separates_generation_and_evaluation_latency` fails on
v0.3.0 (`TrialResult` has no `generation_ms`) and the pre-fix code path
shows the single measurement spanning both phases.

### Correction

Trials now record `generation_ms` (model call only, provider retries and
backoffs included), `evaluation_ms`, `total_ms` and the pre-existing
`queue_ms`. The historical `latency_ms` field keeps generation-latency
semantics for new runs. Statistics, the markdown report, the terminal
tables, the CSV export, the comparison indicators, the dashboard and the
trial explorer label each duration; runs produced before 0.3.1 are
marked legacy (their recorded mixed latency is displayed as-is, never
recomputed). `compare` warns when latency semantics differ between runs.

### Validation

Unit tests assert generation and evaluation independence with a slow
evaluator, preservation of latencies for failed requests, legacy
fallback in `compute_stats`, and legacy report loading.

## P1 — Judge budgets and accounting

### Confirmed defects

- `BaseJudge` mutated `calls_made` and `cost_usd` from concurrent worker
  threads without synchronization; the `max_calls` cap could be exceeded
  under load.
- `budget_usd` was checked against already-observed spend only, with no
  admission control, and was presented without qualification.
- Outcomes attached tokens and cost only for valid verdicts: a billed
  call whose verdict failed to parse contributed nothing to recorded
  usage.

### Correction

Call admission is now an atomic `reserve_call()` under a lock; monetary
accounting is updated under the same lock. `plan_check` additionally
refuses plans whose output-token cost alone (a lower bound computable
when `max_tokens` and pricing are known) exceeds `budget_usd`;
`budget_usd` is documented and announced as a stop-on-observed guard,
because input-token cost cannot be pre-bounded. Every evaluation now
records calls, responses received, valid verdicts, invalid verdicts,
network errors and provider retries (exposed by `ProviderResponse.attempts`),
and attaches token/cost usage to the outcome regardless of verdict
validity, with a known-cost count for coverage.

### Validation

Unit tests cover concurrent `reserve_call` (40 threads, cap 10),
concurrent `evaluate` under `max_calls`, billed-but-invalid calls,
network errors, retry counting, partial cost coverage, the plan-time
lower-bound refusal and budget-stopped outcomes.

## P1 — Metric separation

### Confirmed defect

`compute_stats()` pooled every binary-evaluable trial into one
population: exact match, contains, regex, JSON schema conformance and
code tests all fed `answer_accuracy`.

### Correction

`answer_accuracy` now covers deterministic metrics only. New fields
carry `json_schema_conformance`, `code_eval_pass_rate`,
`code_tests_passed`/`code_tests_total`, `judge_score_mean` and judge
coverage, each with its own denominator, grouped per model and
evaluator. The aggregate indicators (`evaluable`, `evaluation_coverage`,
`overall_pass_rate`) keep their historical definitions and are
documented as cross-evaluator aggregates. Markdown, terminal, JSON and
HTML outputs gained an evaluation breakdown; the comparison report
shows the per-evaluator indicators instead of mixing them.

### Validation

Mixed-dataset tests assert each population stays separate; a pure
`json_schema` run now reports `answer_accuracy: n/a` instead of silently
reusing the conformance rate.

## P1 — Reevaluation provenance

### Confirmed defect

`evaluate` reused the source manifest as-is and matched stored answers
to dataset entries by id only. A dataset whose prompt changed under a
kept id silently re-judged an answer against a different question.

### Correction

Matching is verified before re-evaluation: an identical dataset
fingerprint verifies all entries; an embedded dataset snapshot allows
per-entry prompt/reference/system/metric fingerprint checks; changed
entries are reported as conflicts and kept unchanged; without either
source of truth the match is flagged unverified in the output and the
manifest. Reevaluated runs record `source_run` (generation metadata:
benchmark, date, version, seed, dataset sha, models, path) and
`reevaluation` (date, version, evaluators, judge rubric fingerprint,
dataset sha, matching summary) as separate manifest blocks; the original
results are never modified.

### Validation

CLI tests cover the verified, conflicting and unverified paths and
assert the original trials survive untouched.

## P1 — Run comparability

### Confirmed defect

`compare` warned about datasets, seeds, repeats, concurrency, versions
and model configuration, but ignored evaluators: two runs judged with
different rubrics or judge models were presented side by side without a
warning, and the existing paired-comparison module was not used at all.

### Correction

Comparability checks now cover judge rubric fingerprints, judge models,
judge presence (including "unknown for pre-0.3.1 runs"), code evaluation
configuration and mixed latency semantics. When exactly two runs share
an identical dataset, per-model paired differences (repeats averaged per
question, bootstrap interval, explicit unit count) are computed and
shown in the terminal and the HTML report; paired intervals are never
produced for unpairable runs.

### Validation

Unit tests cover each warning trigger and the paired computation
gate (identical dataset, two runs, shared questions).

## P2 — Pairwise policy

### Confirmed defect

`pairwise_outcome()` filtered ties before comparing preferences: a win
combined with a tie counted as a confirmed win, losing information.
Provider exceptions reached the record unmasked.

### Correction

Outcomes now distinguish `win:<model>` (concordant), `tie` (concordant),
`mixed_verdict` (win + tie), `disagreement`, `incomplete`,
`judge_error` and `unavailable`; both verdicts are always kept.
Provider errors pass through `safe_error_message()`; pairwise judge
calls honor `max_calls` and record token/cost usage per judgment with
coverage in the summary. A failed comparison does not abort the
remaining ones.

## P2 — JSON Schema and rubrics

### Confirmed defect

`extract_json()` returns `(None, error)` on failure, but
`evaluate_json_schema()` and the verdict parsers tested `parsed is None`
— the valid JSON value `null` was indistinguishable from a parse
failure, and a schema allowing `null` could never validate a `null`
response.

### Correction

Callers now branch on the error channel; `null` parses successfully and
validates against `{"type": "null"}`. Rubrics reject duplicate criterion
ids. Edge cases (nested objects, arrays, special characters, numeric
types, local `$ref`, recursive schemas, malformed schemas, remote refs)
are covered by tests.

## P2 — Statistics and exports

Statistics metadata now reports units, excluded question ids and the
conditional nature of the pass-rate interval ("evaluated trials only"),
plus an explicit note that intervals are not significance tests.
Edge cases (single question, identical values, disjoint datasets) are
tested. The CSV export adds generation/evaluation/total latency columns
and a separate `evaluations.csv` with evaluator type, status, scores,
judgment counts, evaluation tokens and cost, code test totals and JSON
error counts; missing values stay empty, never zero, and formula
neutralization applies to both files.

## Docker image reproducibility

The default evaluation image is pinned by digest:
`python:3.12-slim@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b`.
The digest is the one the adversarial suite executed against on this
machine (verified against the daemon's `RepoDigests` and re-verified by
a full run after pinning). To update: pull the desired tag
(`docker pull python:3.12-slim`), read the digest printed by the pull or
`docker image inspect`, update `CodeEvalConfig.image` and the digest in
`.github/workflows/docker-integration.yml`, then re-run the Docker
integration workflow. The runtime never falls back to host execution:
when Docker is unavailable the outcome is `unavailable` and the model is
not penalized.

## Checked and already correct

- Secret masking (`mask_secrets`, ordering of bearer/URL/query/kv
  patterns) — no regression found; extended coverage maintained.
- Transient-only retries with bounded `Retry-After` — unchanged and
  correct; attempts are now surfaced for accounting.
- KeyboardInterrupt handling (exit 130, no reports written) — unchanged.
- Container hardening flags (no network, read-only rootfs, non-root
  user, dropped capabilities, no-new-privileges, memory/cpu/pids limits,
  `--rm`) — kept; the pinned digest and explicit `docker rm -f` cleanup
  strengthen them.
- `results/` stays gitignored; no benchmark content is published.
